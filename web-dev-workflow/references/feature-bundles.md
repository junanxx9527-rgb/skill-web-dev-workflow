# 配套完整性(Feature Bundles)

核心原则:用户点名的是一个功能的"名字",你要交付的是真实产品里这个功能的**完整闭环**。
但范围不是背清单背出来的,而是推导出来的。

## 闭环思考程序(每次做功能前先跑一遍)

动手前,在心里(或 thinking 里)回答这四个问题:

1. **真实产品里,这个功能的完整闭环是什么?** 用户从看到入口到完成操作再到看到结果,中间经过哪些页面/接口/状态?
2. **数据从哪来、到哪去?** 需要什么表/字段?谁写入、谁读取?要不要分页/排序/过滤?
3. **失败时用户看到什么?** 校验失败、网络错误、权限不足、空数据——每种情况界面长什么样?
4. **权限边界在哪?** 谁能看、谁能改、谁能删?未登录用户呢?A 用户能碰 B 用户的数据吗?

据此列出配套范围。**举一反三,不要只会下面的例子**——例子是帮你校准"全套"是什么粒度的,不是穷举。

## 示例(校准粒度用)

- **"加个 XX 接口"** → 完整 CRUD(确认哪些子操作真的需要)+ 服务端校验 + 列表分页 + 统一错误格式 + 前端调用层封装。
- **"做用户功能"** → 注册 / 登录 / 登出 / 用户主页 / 资料编辑 / 密码重置,全套;以及受保护路由的跳转逻辑。
- **"加个评论功能"** → 发表 + 列表(分页)+ 删除(作者或管理员)+ 校验与防 XSS + 空态("还没有评论")+ 失败提示;
  如果站点有用户系统,评论关联用户;没有,确认匿名方案。
- **任何页面** → 自带 loading 态、空态、错误态、响应式。
- **任何表单** → 客户端即时校验 + 服务端权威校验 + 提交中禁用 + 成功/失败反馈。

## 模式:第一次 vs 第 N 次

- **第一次写某类东西**(第一个 API、第一个表单、第一个页面):先建立可复用的模式(统一错误格式、校验方式、
  前端 API 调用层、布局组件),把模式记进约定文档。这一步多花的时间会在之后每个同类任务里赚回来。
  **具体契约和 Next.js/Vue 现货示例见 `references/patterns.md`,照它落地,别临场现编。**
- **第 N 次**:读约定文档,严格复用已有模式。不要发明第二种错误格式、不要写裸 fetch。

## 确认分级

推导出配套范围后:

- **小配套**(补校验、加错误态、加分页、顺手的小页面):直接做。完成汇报时一句话带过:"顺带补了 X 和 Y。"
- **大动作**(新增依赖、改数据库结构、新增整套页面/模块):动手前用一句话列出计划——
  "做这个功能我打算顺带:A、B、C,OK 的话我一次做完。" 等确认,确认后一次做完,不再中途追问。

判断标准:**用户撤销这个改动的成本**。一个错误态删掉就行(小);一个新依赖或一张新表要迁移回滚(大)。

## 比例感

用户只是改文案、调样式、修个小 bug 时,**不触发**本流程——改完即止。
完整闭环是给"做功能"准备的,不是给每次编辑准备的。把全套流程用在小修改上,和忘了用在功能上一样,都是失败。
