# 交付自查(Delivery Checklist)

汇报"做完了"之前,先过这份清单。目标对齐 SKILL.md 的 MVP 标准:**交付的是能直接往上长的生产级雏形,不是看着能跑的 demo。**
"做完"不等于"代码写完了",而是"验证过、确实能用、且没埋返工的坑"。

## 一、必须跑的硬验证(有就跑,跑完看结果)

按项目实际配置,能跑的都跑,**别只写完代码就说完成**:

1. **类型检查**:`tsc --noEmit` / 框架自带 typecheck(TS 项目)。类型错误不算小事,它常常是真 bug。
2. **构建**:跑一遍生产构建(`build`),确认无报错、无致命警告。构建挂了就是没做完。
3. **Lint / 格式化**:有配置就跑,按项目既有规则,不引入一堆 lint 错误。
4. **测试**:有测试就全跑过;**这次新增/改动的核心流程,补上对应测试**(见下"测什么")。

跑完在汇报里**如实说**:跑了哪几样、结果如何。**绝不谎称"测试通过"而没真跑。** 跑不了(环境缺失等)就说明原因,别假装。

## 二、测什么(MVP 的测试尺度)

MVP 不追求覆盖率数字,但**关键路径必须有测试兜底**——因为它要"往上长",没有测试的地基一升级就塌。优先级:

- **关键业务流程(必测)**:核心 happy path(如注册→登录→发帖→看到帖子)走通的集成/端到端冒烟测试。一条主链路至少一个测试。
- **带分支的纯逻辑(该测)**:校验规则、权限判断、价格/计数等计算——这些错了影响大、且单测便宜。
- **失败路径(挑重要的测)**:越权被拒、校验失败返回 400、未登录跳转——安全相关的失败路径尤其要测。
- **可以先不测**:纯展示 UI、第三方库内部、一次性脚本。别为凑覆盖率写空测试。

判据还是 MVP 标准:**这条链路日后升级时,有没有测试能告诉你"有没有改坏"。** 有就够,没有就补。

## 三、交付前自查清单(沉默执行,有问题才报)

- [ ] **跑通了上面的硬验证**,结果如实记录。
- [ ] **关键路径有测试**,新增功能的主链路被覆盖。
- [ ] **页面三态齐全**:有数据的页面 loading / 空 / 错误态都在,且真能触发(不是写了不生效)。
- [ ] **响应式**:主要断点(手机/桌面)下不破版。
- [ ] **安全基线过了**`security-checklist.md`:服务端校验、鉴权与水平越权、密钥进 env、错误不泄露内部。
- [ ] **环境与密钥**:`.env.example` 齐全且最新,真实密钥没进代码/提交history,`.gitignore` 到位。
- [ ] **控制台干净**:主要页面无报错、无明显警告(如 React key、未捕获 promise)。
- [ ] **没有埋返工坑**:没有写死的假数据冒充真逻辑、没有 `// TODO: 以后再做鉴权` 这类把地基拖欠到未来的东西。
      MVP 可以少做功能,但已做的部分不能是"先这样以后重写"。
- [ ] **约定文档同步**:这次确立的新模式/新决策记进了约定文档(见 `intake.md` / `patterns.md`)。

## 四、汇报纪律

- **如实说跑了什么、结果如何**:"跑了 typecheck + build + 单测,均通过;e2e 暂未配,核心流程手测走通。" 这种具体陈述,而不是笼统一句"已完成测试"。
- **没做到的、跳过的、有意偏离的,主动点出**,别等用户发现。失败的测试要贴出来,不掩盖。
- 一切默认沉默执行,只有**未覆盖项、偏离项、失败项**才进汇报——用户想知道的是"哪里还没稳",不是"我做了多少例行检查"。
