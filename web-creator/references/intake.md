# 启动对齐(Intake)

目的:在动手前一次性对齐关键决策,避免边做边碎问,也避免做完才发现方向错了。
对齐结果写入项目内约定文档(优先 `CLAUDE.md`,已有文档体系的项目可用 `docs/conventions.md`),
后续全程遵守,**不再重复询问**。

## 路径一:全新项目

主动发起一轮结构化沟通,一次问完。能用 AskUserQuestion 这类结构化提问工具就用,否则把问题整理成一组清单一次性列出。
问题按以下顺序,每个都要有,不要拆成多轮:

1. **项目类型与目标用户**:这是什么产品?给谁用?(个人博客、内部工具、SaaS、电商……规模感决定后面所有推荐)
2. **技术栈**:给 2~3 个方案,每个写清取舍,并结合项目规模给出你的推荐,由用户拍板。例如:
   - 小型内容站:Astro/Next.js 静态优先(简单、SEO 好) vs 全栈 Next.js(以后好加动态功能);
   - 中型应用:Next.js + Prisma + Postgres(生态全) vs SvelteKit(更轻) vs 前后端分离(团队分工需要时);
   - 不要只报名词,一句话说清"什么情况选它"。
3. **是否需要用户系统**:要不要注册/登录?自建还是用 Auth 服务(Clerk/Auth.js/Supabase Auth)?
4. **是否需要多语言(i18n)**:必须现在问。i18n 是架构级决定——路由结构、文案组织、数据库设计都受影响,
   后期补迁移成本很高。哪怕用户暂时只要一种语言,也要确认"以后会不会要",并据此决定是否预留结构。
5. **部署目标**:部署到哪?(Vercel/Cloudflare/自有服务器/Docker……)这影响框架特性取舍和环境变量管理方式。

用户回答后,把结论写入约定文档,格式建议:

```markdown
## 项目约定(启动对齐 YYYY-MM-DD)
- 项目类型 / 目标用户:…
- 技术栈:…(理由一句话)
- 用户系统:有/无,方案:…
- 多语言:需要/不需要/预留结构
- 部署目标:…
- 接口模式:(首次写 API 时补充,见 feature-bundles)
```

## 路径二:已有项目(首次接手)

**不要重新问卷。** 用户最反感的就是项目里明明写着,还被问一遍。流程:

1. 读现有代码和文档:`package.json`/锁文件、框架配置、目录结构、已有的 `CLAUDE.md`/`README`/`docs/`、
   有代表性的一两个接口和页面。
2. 推断出:技术栈、接口风格(错误格式、校验方式、有没有统一调用层)、认证方式、数据库与 ORM、部署方式。
3. 用几行话**简要复述确认**:"我看了下,这是个 X + Y 的项目,接口走 Z 风格,认证用 W——我会照这套惯例来,有出入告诉我。"
   然后直接开工,不等长篇回复。
4. 若项目没有约定文档,把推断结果写成一份(标注"由代码推断"),供后续复用。
5. 推断不出来的关键决策(且确实影响当前任务的)才开口问,问也只问那一两个。

## 共同纪律

- 约定文档是单一事实来源。定过的事,后续任务直接照办;用户改了主意,更新文档。
- 对齐是一次性的:同一项目第二次任务不再走 intake,直接读约定文档。
