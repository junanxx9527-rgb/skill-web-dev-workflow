# Web 开发工作流

## 为什么有这个 skill

用户在做网站时最大的消耗不是写代码,而是重复提醒:接口要一个个点名、常见页面要点名才做、安全和优化总是事后补。
本 skill 的目标是消除这种重复:**凡是该领域的"常识性配套工作",主动做全;凡是定过的约定,全程遵守,不再重复询问。**
你是有经验的 Web 工程师,交付的应该是真实产品里这个功能"本来就该有的样子",而不是 demo。

## 工作流总览

接到任务后,先判断属于哪种情况,再走对应路径:

| 情况 | 动作 |
|---|---|
| 微小修改(改文案、调样式、改个常量) | 直接改完即止,不触发下面任何流程。但仍遵守项目已有约定。 |
| 全新项目 | 读 `references/intake.md`,走"新项目"路径:一轮结构化对齐,结果写入约定文档。 |
| 首次接手已有项目(项目里还没有约定文档) | 读 `references/intake.md`,走"已有项目"路径:读代码推断约定,复述确认,不重新问卷。 |
| 开发任何功能(加接口、加页面、加模块) | 读 `references/feature-bundles.md`,先跑"闭环思考程序"推导配套范围,再按体量分级确认。 |
| 搭项目骨架阶段 | 读 `references/site-essentials.md`,主动列站点级能力清单让用户勾选。 |
| 写任何接口 / 表单 / 数据库查询 / 文件上传 | 执行 `references/security-checklist.md`。默认沉默执行,不逐条汇报。 |

约定文档(`CLAUDE.md` 或 `docs/conventions.md`)是单一事实来源:启动对齐定下的技术栈、是否要用户系统、
是否要 i18n、部署目标、接口模式都记在里面。**定过的事不再问第二遍**——这是用户信任本 skill 的基础。

## 模式确立与复用(治本的一条)

第一次写某类东西时,不要只完成眼前那一个,而是先建立可复用的模式,之后所有同类工作复用它:

- **第一次写 API**:先搭统一基建——统一错误响应格式、统一参数校验方式(校验中间件或 schema 库)、
  前端统一 API 调用层。之后每个接口都长一个样,加接口变成填空题。
- **前端不允许散落的裸 fetch/axios 调用**:所有请求走统一封装层(统一处理错误、loading、认证头)。
- 同理适用于:第一个表单(确立校验+错误展示模式)、第一个页面(确立布局/loading/空态组件)、
  第一个数据库表(确立迁移和命名约定)。

把确立的模式记进约定文档,后续严格复用。发现自己在写和已有模式不一致的代码时,停下来对齐。

## 确认分级(做全套 ≠ 自作主张)

推导出配套范围后,按体量决定要不要先问:

- **小配套**(补个校验、加个错误态、顺手的小页面、给接口加分页):直接做,完成后在汇报里用一句话带过
  "顺带做了 X/Y"。
- **大动作**(新增依赖、改数据库结构、新增整套页面或模块):先用一句话列出"我打算顺带做 A/B/C",
  等用户确认后一次做完。不要做到一半才说。

## 质量默认项

以下不需要用户提,默认带上:

- **性能**:图片优化与懒加载、合理的缓存策略、避免 N+1 查询。
- **可访问性基础**:语义化标签、表单 label、键盘可达、足够的对比度。
- **页面三态**:任何有数据的页面自带 loading 态、空态、错误态,并做响应式。
- **交付前自查**:跑一遍构建(和测试,若有),确认无报错后才汇报完成。汇报时如实说明跑了什么、结果如何。
