# 启动对齐(Intake)

目的:在动手前一次性对齐关键决策,避免边做边碎问,也避免做完才发现方向错了。
对齐结果写入项目内约定文档(优先 `CLAUDE.md`,已有文档体系的项目可用 `docs/conventions.md`),
后续全程遵守,**不再重复询问**。

## 路径一:全新项目

主动发起一轮结构化沟通,一次问完。能用 AskUserQuestion 这类结构化提问工具就用,否则把问题整理成一组清单一次性列出。
问题按以下顺序,每个都要有,不要拆成多轮:

1. **项目类型与目标用户**:这是什么产品?给谁用?(个人博客、内部工具、SaaS、电商……规模感决定后面所有推荐)
2. **技术栈**:**先判断用户有没有能力/意愿做这个决定,再决定怎么处理**——见下方"技术栈:分情况处理"。
   绝不把一堆技术名词甩给一个看不懂的用户让他"拍板"。
3. **是否需要用户系统**:要不要注册/登录?自建还是用 Auth 服务(Clerk/Auth.js/Supabase Auth)?
4. **是否需要多语言(i18n)**:必须现在问。i18n 是架构级决定——路由结构、文案组织、数据库设计都受影响,
   后期补迁移成本很高。哪怕用户暂时只要一种语言,也要确认"以后会不会要",并据此决定是否预留结构。
5. **部署目标**:部署到哪?(Vercel/Cloudflare/自有服务器/Docker……)这影响框架特性取舍和环境变量管理方式。
   同样:不懂的用户不会知道"Vercel 还是 Docker",改问"有没有人帮你维护服务器,还是希望尽量省心免运维",由 Claude 据此定。

### 技术栈:分情况处理

技术栈是**手段**,用户真正能回答的是**目的**(产品给谁用、要不要登录、内容谁来发、以后想加什么、希不希望省心)。
所以先用一句话探明用户处在哪种情况,再走对应分支:

- **情况 A:用户有明确技术偏好**("我要用 Next.js")→ 照他的来,只在他的选择和需求明显冲突时提醒一句。
- **情况 B:用户懂技术、但没拍定**→ 给 2~3 个方案,每个一句话说清"什么情况选它",结合项目规模给出推荐,由用户拍板。例如:
  - 小型内容站:Astro/Next.js 静态优先(简单、SEO 好) vs 全栈 Next.js(以后好加动态功能);
  - 中型应用:Next.js + Prisma + Postgres(生态全) vs SvelteKit(更轻) vs 前后端分离(团队分工需要时)。
- **情况 C:用户不懂技术 / 明说"你定就行"**→ **Claude 自行决定,不要让用户在技术选项里做选择**。流程:
  1. 把决策依据建立在用户**已经回答的目的层问题**上(项目类型、规模、用户系统、i18n、是否要省心免运维),不为选栈再追问技术细节。
  2. **按项目类型推导出最合适的栈**(见下方"按项目类型推导技术栈"),不要套一个固定默认。
  3. 直接拍这套方案,**只用人话讲理由**("这套最省心、以后好加功能、部署免费"),不罗列取舍矩阵、不甩技术名词。
  4. 写进约定文档时标注"**由 Claude 选定,可随时改**",给用户一个低成本反悔口,而不是开头就逼他承诺。

**判断要点**:能否区分 B 和 C,靠的是用户对第 1 题等问题的回答方式和用词,不是直接问"你懂不懂技术"(那很冒犯)。
拿不准时,默认按 C 处理更安全——替用户扛下决定,比逼他选他看不懂的东西好。

### 按项目类型推导技术栈

**没有一套"默认栈"——栈是从项目类型和需求推导出来的结果,不同项目本就该用不同的栈。**
推导时按这几个维度权衡,让需求来选栈,而不是拿栈去套需求:

- **内容以谁为主**:静态内容为主(博客/文档/落地页) vs 大量动态交互(后台/SaaS)——决定要不要全栈框架、要不要数据库。
- **数据复杂度**:无数据 / 简单读写 / 关系复杂——决定无 DB、轻量 DB(SQLite)、还是关系库(Postgres)+ ORM。
- **用户系统与规模**:无登录 / 小规模自建 / 大规模 → 决定认证方案的轻重。
- **省心程度与部署约束**:希望零运维免费部署,还是必须自有服务器/特定云。
- **SEO 与首屏**:面向公众搜索流量的,优先 SSR/SSG 能力强的方案。

**类型 → 倾向(只为校准粒度,不是查表对号,更不是穷举)**:

- 个人博客 / 文档 / 营销落地页 → 静态优先(Astro / Next 静态导出),SEO 好、几乎零运维,通常不需要数据库。
- 内容站但要评论/订阅等少量动态 → 全栈框架(Next.js / SvelteKit)起步,轻量 DB。
- 中后台 / 内部工具 → 全栈框架 + 关系库 + ORM,认证从简(够用即可)。
- SaaS / 多用户产品 → 全栈框架 + Postgres + 成熟认证(Auth.js / Clerk),考虑多租户与权限。
- 电商 → 视体量,小店可用成品(如 Shopify/无头方案),自建则全栈 + 关系库 + 支付/订单/库存配套。

**铁律**:用户已有技术栈、团队约定、或宿主环境限制(只能部署到某处)时,一律服从,不要按偏好另选。
推导出的栈和理由写进约定文档,并注明可改。

用户回答后,把结论写入约定文档,格式建议:

```markdown
## 项目约定(启动对齐 YYYY-MM-DD)
- 项目类型 / 目标用户:…
- 技术栈:…(理由一句话)
- 用户系统:有/无,方案:…
- 多语言:需要/不需要/预留结构
- 部署目标:…
- 接口模式:(首次写 API 时补充,见 feature-bundles)
```

## 路径二:已有项目(首次接手)

**不要重新问卷。** 用户最反感的就是项目里明明写着,还被问一遍。流程:

1. 读现有代码和文档:`package.json`/锁文件、框架配置、目录结构、已有的 `CLAUDE.md`/`README`/`docs/`、
   有代表性的一两个接口和页面。
2. 推断出:技术栈、接口风格(错误格式、校验方式、有没有统一调用层)、认证方式、数据库与 ORM、部署方式。
3. 用几行话**简要复述确认**:"我看了下,这是个 X + Y 的项目,接口走 Z 风格,认证用 W——我会照这套惯例来,有出入告诉我。"
   然后直接开工,不等长篇回复。
4. 若项目没有约定文档,把推断结果写成一份(标注"由代码推断"),供后续复用。
5. 推断不出来的关键决策(且确实影响当前任务的)才开口问,问也只问那一两个。

## 共同纪律

- 约定文档是单一事实来源。定过的事,后续任务直接照办;用户改了主意,更新文档。
- 对齐是一次性的:同一项目第二次任务不再走 intake,直接读约定文档。
